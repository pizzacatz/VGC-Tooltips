# Technical Vocabulary — this project, three ways

The same story told three times: (1) in full industry jargon, (2) in plain
language with the matching technical term after each phrase, (3) as a
glossary table anchoring every term to the moment it appeared in this
project. Read 1 to test yourself, 2 to decode it, 3 to make it stick.

---

## 1. The jargon-dense version

### What it is

VGC Tooltips is a **browser extension** targeting both **Manifest V3**
(Chrome) and the **WebExtensions API** (Firefox), distributed as an
unpacked/**`.crx`**-packaged bundle for Chrome and an **AMO** (addons.mozilla.org)
submission for Firefox. It runs a single **content script** (`content.js`)
**injected** into a fixed allowlist of hosts declared in `manifest.json`'s
`content_scripts.matches`, plus a **popup** (`popup.html`/`popup.js`) wired
to the toolbar `action`. The only requested **permission** is `storage`,
used exclusively for a single on/off toggle synced via `chrome.storage.sync`
/ `browser.storage.sync` — a **cross-browser compatibility shim**
(`const vgcApi = typeof browser !== 'undefined' ? browser : chrome`)
papers over the fact that Firefox's `browser.*` namespace is
**promise-only** while Chrome's `chrome.*` is callback-first-but-also-
promise-capable, so the code is written to the promise form both share.

### Sensing/scanning

The extension's core is a **DOM scanner**: a **`TreeWalker`**
(`NodeFilter.SHOW_TEXT`) walks each page's designated **container**
elements collecting **text nodes**, tests them against a single compiled
**regular expression** built from every known term (escaped via
`escapeRegExp` and joined with **negative lookaround** assertions —
`(?<![a-zA-Z0-9_])...(?![a-zA-Z0-9_])`), and on a match **splices** the text
node into a **`DocumentFragment`** of plain text nodes and `<span>`
elements — never through **`innerHTML`** re-parsing, which is the
deliberate defense against **DOM-based XSS**: a chat line like
`Pikachu <img src=x onerror=...>` is already **HTML-escaped** by the host
page, and reassembling it via `innerHTML` would un-escape and execute it,
so the scanner only ever calls `textContent`/`createTextNode` on
page-derived text. New content arriving later (Showdown's live battle log)
is caught by a single document-level **`MutationObserver`** rather than the
polling loop it replaced, with `observer.takeRecords()` used to **drain**
the mutation queue generated by the scanner's own edits so it can't
**re-trigger itself**.

Because one string can name more than one game object (`Metronome` is both
a move and an item), the term index (`vgcIndex`) maps each name to a
**candidate list** instead of a single record — a design that replaced an
earlier one where the **last write won** and one category silently
**shadowed** the other. Disambiguation (`resolveCategory`) is **site-aware**:
each of four `SITE_PROFILES` declares either **structural scopes** (CSS
selectors that state the category outright, e.g. Limitless's `.item` /
`.ability` elements) or **wording cues** (regexes tested against
**up-to-40-character context windows** gathered across sibling **element
boundaries** via `textAround`, e.g. Showdown's `"used "` prefix meaning a
move). Cues are anchored patterns, not loose substring tests, to avoid
**false positives** from a game term that happens to sit near the trigger
word. When no rule resolves the ambiguity, a static
**`CATEGORY_PRIORITY`** array acts as the tie-breaker. Category resolution
also drives the highlight's **category-scoped CSS class**
(`vgc-type-move`, etc.), so the underline color and the tooltip content are
guaranteed to **agree** by construction rather than by two code paths
staying in sync.

Hover behavior itself is **event delegation**: one `mouseover` /
`mousemove` / `mouseout` listener on `document`, tested against
`e.target.classList` rather than one listener per highlighted span, so
dynamically inserted spans need no rebinding. Tooltip **positioning** is
**viewport-clamped** — it flips to the opposite side of the cursor when the
default placement would overflow `window.innerWidth`/`innerHeight`.

### The hard parts

Champions' vocabulary for a move's tagged properties is **Classification**,
a **closed, hand-curated twelve-item allowlist** (`CLASSIFICATIONS` in
`build.js`) mapped from Pokémon Showdown's internal **move flags** — of
which Showdown tracks 39, most either engine plumbing or simply un-named by
the game. This was deliberately built as an **allowlist rather than a
denylist**: a denylist previously let unrecognized flags (`allyanim`,
`noSketch`) leak into the tooltip as spurious labels while silently
dropping `heal`, which *is* official. Four Classification memberships
cannot be **derived** from the Showdown source at all and are instead a
**hand-maintained overlay** (`CHAMPIONS_OVERLAY`) — two flags
(`explosive`, `mental`) are **Champions-native**, absent upstream entirely,
and two (`slicing`, `sound`) exist upstream but **diverge** on five specific
moves, verified against a separate **MCP** (`champions-logic`) authoritative
data source. The overlay is **self-validating**: build.js throws a fatal
error if an overlay move name no longer matches `moves-data.ts` (silent
upstream **rename** would otherwise just drop the Classification with no
error), and warns if an overlay entry has become **redundant** because the
source now carries that flag on its own.

`contact` — the single most consequential move flag in battle (it gates
Rough Skin, Static, Flame Body, Rocky Helmet, Iron Barbs) — is deliberately
excluded from `classifications`: Champions does not label it as one, so it
ships as an independent boolean field and renders as a trailing pill,
keeping the labeled Classifications an accurate list of only what the game
itself names.

### The build process

`build.js` is a **Node.js build script** that registers `ts-node` in
**`transpileOnly`** mode (type-checking skipped for speed) so it can
`require()` Pokémon Showdown's **TypeScript source modules**
(`pokedex.ts`, `moves-data.ts`, `moves-text.ts`, `items.ts`, `abilities.ts`,
`natures.ts`) directly, without a separate compile step. Each **builder
function** projects that upstream shape down into a minimal runtime
**data library** (flat `name → record` JSON, `pokemon.json`/`moves.json`/
etc.) that the content script `fetch()`es at page-load via
`vgcApi.runtime.getURL(...)`. Targets are selectable via **CLI arguments**
or, absent those, an **interactive multiselect prompt** (`prompts`
package). After a successful build, three **static consistency checks**
run: `checkCollisions()` (cross-library name clashes), `checkManifest()`
(the `content_scripts.matches` / `web_accessible_resources.matches` /
`.resources` lists must agree, or the extension **loads with dead
fetches**; the Firefox `gecko.id` must be present, or Firefox's per-add-on
**keyed storage** silently orphans the popup toggle; `manifest.json` and
`package.json` **versions** must match, normalized to major.minor.patch, or
browsers never see an update as available). A final `syncDist()` step
**mirrors** every shipping file into `/dist`, the actual **load target**
for both "Load Unpacked" testing and Firefox packaging, so the repo root
and `/dist` cannot silently drift apart. Firefox-specific tooling
(`web-ext lint`, `web-ext build`, `web-ext run`) runs against `/dist` only,
producing a **signed-ready `.zip` artifact** for AMO upload.

## 2. The plain-language version

This project is a **browser add-on** (**browser extension**) that works in
both Chrome and Firefox, even though the two browsers use slightly
different underlying systems (**Manifest V3** for Chrome, the
**WebExtensions API** for Firefox). It's packaged as a `.crx` file for
Chrome and submitted to Mozilla's add-on store (**AMO**) for Firefox. Most
of the work happens in one script that gets automatically inserted into a
short list of approved websites (**content script**, `content.js`), plus a
small popup window from the toolbar icon (`popup.html`/`popup.js`) that
holds just one on/off switch. That switch is the *only* thing the
extension is allowed to remember (**the `storage` permission**), and it's
kept in sync between the popup and the page script using a storage API
that behaves slightly differently in each browser — so the code checks
which browser it's running in and picks the matching version
(**compatibility shim**).

The heart of the extension is a scanner that walks through all the text on
a page (**DOM scanner**, using a browser tool called a `TreeWalker` that
visits every piece of text one at a time — **treewalker**) looking for
Pokémon names, moves, items, etc. It builds one big pattern that matches
every known term at once (**regular expression**), carefully written so it
only matches whole words and not word-fragments (**word-boundary
matching**). When it finds a match, it very carefully swaps just that
piece of text for a styled, hoverable version — using safe browser methods
that only ever insert *text*, never re-interpreted HTML
(**`textContent`/`createTextNode`**, avoiding **`innerHTML`**). This
matters because a chat message someone typed could contain something that
*looks* like an HTML tag; if the page ever re-parsed that as real markup
it could run attacker-controlled code (a **cross-site scripting / XSS**
risk) — so the scanner is built to never let user-typed text become
anything other than inert text. When new lines get added live to a
Pokémon Showdown battle log, a browser feature that watches for page
changes (**MutationObserver**) notices and scans just the new part,
instead of the old approach of re-checking the whole page every couple of
seconds.

Some names mean two different things — "Metronome" is both a held item and
a move — so the extension keeps a list of *all* possible meanings for each
name instead of just picking one and forgetting the other (avoiding a bug
where **one meaning would silently overwrite the other**). To figure out
which meaning is meant on any given page, it uses two different tricks
depending on the site: some sites mark their data up with clear structure
(an item always sits inside an element the page itself labels `.item`, an
ability inside `.ability`, and so on — **structural detection**), while
others (Pokémon Showdown's chat)
have to be guessed from the surrounding sentence, like noticing the word
"used" right before a name means it's a move (**contextual/wording
clues**). If neither trick gives an answer, it just guesses the most
likely meaning (moves are the most likely guess, since battle logs mention
them constantly). Hovering itself is handled by one single listener for
the whole page rather than attaching one to every single highlighted word
(**event delegation**), which keeps things fast even on a busy chat log,
and the tooltip repositions itself so it never runs off the edge of the
screen.

One competitive-format detail gets special handling: Pokémon Champions (a
newer, stricter Pokémon ruleset) labels twelve specific move properties
with its own names ("Sound-Based," "Ball & Bomb," etc. — **Classification**),
which map to Pokémon Showdown's internal list of 39 much more technical
tags (**move flags**), most of which the game never shows players at all.
The mapping is deliberately a short "these are the ones that matter" list
(an **allowlist**) rather than a "hide these specific ones" list
(**denylist**), because the denylist approach previously let junk labels
leak through while accidentally hiding a real one. Four of the twelve
labels can't be figured out automatically from the Pokémon Showdown data at
all — two properties don't exist in that data source, and two exist but
are assigned to different moves than in Champions — so those four are
listed out by hand and double-checked against a second, official reference.
If the underlying data is ever renamed by an update, the build deliberately
**fails loudly** rather than quietly losing that label.

The whole system is generated, not hand-typed: a script
(`build.js`) reads Pokémon Showdown's own raw data files (written in
TypeScript, a stricter dialect of JavaScript) directly, without a separate
compile step (using a bridge library, **ts-node**, in a fast
"skip the type-checking" mode), and boils each one down into a small,
fast-loading data file (**JSON**) that the extension fetches when a page
loads. After building, the script runs several sanity checks that would
otherwise fail silently and look like unrelated bugs: are there any name
collisions between files, does the list of sites the script is allowed to
run on match the list of sites it's allowed to fetch data on (miss one and
the extension loads but fetches nothing — indistinguishable from
"unsupported site"), is Firefox's required add-on ID present (miss it and
the popup toggle silently does nothing in Firefox only), and do the two
version numbers in the project agree (miss it and browsers never notice
an update exists). Finally, every file that actually ships gets copied
into a `/dist` folder, which is the version actually loaded for testing and
the version packaged and uploaded to Mozilla's store — so there's only one
place a stale copy could hide.

## 3. Glossary — term → meaning → where it happened here

### Browser extension platform

| Term | Plain meaning | In this project |
|---|---|---|
| **browser extension** | small program a browser loads to modify pages | the whole project — Chrome and Firefox builds |
| **Manifest V3** | Chrome's current extension config format/rules | `manifest.json`'s `manifest_version: 3` |
| **WebExtensions API** | the shared cross-browser extension API standard | Firefox's implementation of the same `manifest.json` |
| **content script** | JS auto-injected into matching pages | `content.js`, injected via `content_scripts` |
| **popup** | the small window from the toolbar icon | `popup.html` / `popup.js`, the tooltip on/off toggle |
| **`action`** | manifest key wiring an icon to a popup | `manifest.json`'s `action.default_popup` |
| **permission** | a capability the extension must declare to use | `"permissions": ["storage"]` — the only one requested |
| **`web_accessible_resources`** | files a content script may `fetch()` from the page | the five `.json` libraries, listed per host |
| **host match pattern** | a URL pattern granting/scoping access | `*://play.pokemonshowdown.com/*` etc. in both match lists |
| **`browser_specific_settings.gecko.id`** | Firefox's required add-on identifier | set in `manifest.json`; gates `storage.sync` working at all |
| **`.crx`** | Chrome's packaged/signed extension file format | `VGC-Tooltips.crx`, `dist.crx` |
| **AMO** | addons.mozilla.org, Firefox's extension store | target of `npm run package:firefox`'s output zip |
| **`web-ext`** | Mozilla's CLI for linting/running/packaging extensions | `lint:firefox`, `run:firefox`, `package:firefox` scripts |
| **`storage.sync`** | a small cross-device key/value store extensions get | the single `tooltipsEnabled` boolean |
| **compatibility shim** | code bridging two incompatible APIs | `const vgcApi = typeof browser !== 'undefined' ? browser : chrome` |
| **promise-based API** | async result delivered via `.then()`, not a callback | why `vgcApi.storage.sync.get(...).then(...)` is used, not a callback arg |

### DOM scanning & security

| Term | Plain meaning | In this project |
|---|---|---|
| **DOM** | the browser's live, structured model of a page | what the scanner walks and edits |
| **TreeWalker** | a browser API for visiting nodes of a given type | `document.createTreeWalker(root, NodeFilter.SHOW_TEXT, ...)` in `collectTextNodes` |
| **text node** | a DOM node holding raw text, no markup | what `wrapTextNode` matches against and replaces |
| **event delegation** | one listener catching events from many descendants | single `document`-level `mouseover`/`mouseout` listeners |
| **regular expression (regex)** | a pattern describing text to match | the single compiled term-matching pattern in `buildRegex` |
| **negative lookaround** | asserting what is/isn't adjacent without consuming it | `(?<![a-zA-Z0-9_])(...)  (?![a-zA-Z0-9_])` — whole-word matching |
| **`DocumentFragment`** | an off-DOM container batched into the page at once | built in `wrapTextNode` before `textNode.replaceWith(fragment)` |
| **`textContent` / `createTextNode`** | inserting literal text, never parsed as markup | how every page-derived string reaches the DOM here |
| **`innerHTML`** | assigning a string that gets re-parsed as HTML | deliberately *avoided* for page text; used only for the tooltip's own fixed template strings |
| **XSS (cross-site scripting)** | attacker-controlled text executing as code | the exact risk the `textContent`-only rule defends against (see README's `lint:firefox` note) |
| **MutationObserver** | a browser API notified when the DOM changes | watches for new Showdown battle-log lines, replacing an earlier polling loop |
| **`observer.takeRecords()`** | draining an observer's pending mutation queue | called after handling mutations, so the scanner's own edits don't re-trigger it |
| **event loop feedback / self-triggering** | a listener reacting to its own side effects | the loop `takeRecords()` prevents |

### Term resolution & disambiguation

| Term | Plain meaning | In this project |
|---|---|---|
| **name collision** | one string with more than one valid meaning | `Metronome` is both a move and an item |
| **candidate list** | keeping every possible match instead of one | `vgcIndex[name]` is an array, not a single record |
| **structural scope** | resolving meaning from the enclosing markup | Limitless's `.item`/`.ability`/`.attacks` selectors in `SITE_PROFILES` |
| **wording cue** | resolving meaning from surrounding phrasing | Showdown's `/\bused\s+$/i` before-text test |
| **anchored pattern** | a regex pinned to a specific position, not a loose substring | cues are tied to sentence-relative positions to avoid false positives |
| **context window** | a bounded span of surrounding text to test | the 40-character `CONTEXT_CHARS` budget in `resolveCategory` |
| **priority ordering / tie-break** | a default choice when no rule decides | `CATEGORY_PRIORITY = ['move', 'pokemon', 'ability', 'item', 'nature']` |
| **site profile** | per-site config for containers/scopes/cues | each object in `SITE_PROFILES` (Showdown, PokePaste, two Limitless variants) |

### Data pipeline & build

| Term | Plain meaning | In this project |
|---|---|---|
| **TypeScript source** | Showdown's typed `.ts` data files | `pokedex.ts`, `moves-data.ts`, `moves-text.ts`, `items.ts`, `abilities.ts`, `natures.ts` |
| **ts-node** | runs TypeScript directly via Node, no separate compile step | registered at the top of `build.js` |
| **transpile-only mode** | skipping type-checking for speed | `transpileOnly: true` in the `ts-node` config |
| **data library** | a flat generated JSON lookup table | `pokemon.json`, `moves.json`, `items.json`, `abilities.json`, `natures.json` |
| **build script** | code that generates shipping artifacts from source | `build.js`, run via `npm run build` or `node build.js <targets>` |
| **allowlist** | listing only what's permitted, everything else excluded | `CLASSIFICATIONS` — 12 named flags out of Showdown's 39 |
| **denylist** | listing what to exclude, everything else passes | the rejected earlier approach that leaked `allyanim`/`noSketch` and dropped `heal` |
| **hand-maintained overlay** | data added manually because it can't be derived | `CHAMPIONS_OVERLAY` for `explosive`/`mental`/`slicing`/`sound` |
| **fail-fast validation** | erroring immediately instead of degrading silently | `build.js` throws if an overlay move name no longer matches `moves-data.ts` |
| **redundancy check** | flagging manual data now duplicated by the source | the `overlayRedundant` warning in the `moves()` builder |
| **static consistency check** | verifying invariants at build time, not runtime | `checkCollisions()`, `checkManifest()` |
| **CLI arguments vs interactive prompt** | scripted input vs a menu when none given | `node build.js moves items` vs the `prompts` multiselect fallback |
| **mirroring / sync** | copying the same files to a second location in lockstep | `syncDist()` copying `DIST_FILES` into `/dist` |
| **version mismatch check** | verifying two declared versions agree | `manifest.json` vs `package.json`, normalized to major.minor.patch |

### Rendering & styling

| Term | Plain meaning | In this project |
|---|---|---|
| **CSS custom property (variable)** | a named, reusable style value | `--type-fire`, `--move-border-color` etc. in `styles.css` |
| **data attribute** | a custom HTML attribute carrying app state | `data-vgc-site` on `<html>`, letting CSS defer to a site's own text color |
| **viewport clamping** | repositioning an element so it stays on-screen | the tooltip's flip-to-opposite-side logic in the `mousemove` handler |
| **CSS Grid** | a layout system arranging items in rows/columns | `.vgc-stat-grid` (3/4/2-column variants for Pokémon/move/nature tooltips) |

### Domain-specific data modeling

| Term | Plain meaning | In this project |
|---|---|---|
| **move flag** | Showdown's internal tag for a move's properties | the 39 keys checked in `moves-data.ts`'s `move.flags` |
| **Classification** | Champions' own term for a labeled move property | the 12-entry `CLASSIFICATIONS` map, rendered as pills |
| **Stat Alignment** | Champions' official term for what Showdown calls Nature | `natures.json`, matched under both spellings in `content.js` |
| **MCP (Model Context Protocol) server** | an external tool/data source an AI agent can query | `champions-logic`, used to verify all 145 Classification assignments |
